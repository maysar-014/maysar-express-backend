# Requirements Document

## Introduction

The `run-lifecycle-checks.mjs` script is the primary end-to-end health verification tool for the Maysar platform. It runs HTTP API calls against a live server using seeded test users (admin, buyer, seller, courier) and reports pass/fail counts per lifecycle step.

The current script covers ten lifecycles (LC-01 through LC-10), but coverage is shallow and leaves entire services untested:
- The request/quote service (FLOW-040, FLOW-041) is entirely absent.
- Logistics coverage is limited to a single quote call; delivery tracking, fulfillment options, COD OTP, and maps routing are missing.
- The production plan lifecycle is absent.
- Auth only tests login/logout; token refresh and password reset are not exercised.
- Order fulfillment tests a single state transition instead of walking the full state machine.
- Analytics, inventory, and compliance steps are thin.
- The commission service (FLOW-017, FLOW-018) has zero coverage.
- The payment service (FLOW-034) has zero coverage.
- The notification service (FLOW-031) has zero coverage.
- The user management service (FLOW-057, FLOW-058) has zero coverage.
- The training service (FLOW-055, FLOW-056) has zero coverage.
- The enabler service (FLOW-021, FLOW-022) has zero coverage.
- The business-registry admin flows (FLOW-009) — verify, suspend, documents — have zero coverage.
- The catalog admin flows (FLOW-011) — buy-box, pricing, reviews — have zero coverage.

This feature expands the script to address all of these gaps while preserving the existing structure and output format.

## Glossary

- **Lifecycle (LC)**: A numbered, end-to-end sequence of API calls that exercises one major system feature from start to finish.
- **Step**: A single HTTP API call within a lifecycle, recorded as pass/fail by the `step()` helper.
- **Seeded Users**: The four fixed test accounts (admin, buyer, seller, courier) defined in `USERS` that have pre-existing data in the database.
- **Request Service**: The custom procurement request service at `/api/request` that handles the full buyer → provider → quote → order flow.
- **Request_Request**: A procurement request entity with lifecycle states SUBMITTED → ASSESSING → NEEDS_CLARIFICATION → FULFILLABLE → QUOTE_PUBLISHED → CONVERTED / CANCELLED / EXPIRED.
- **Assessment Link**: A secure single-use token-based link generated by the provider allowing the buyer to review and accept a quote without JWT authentication.
- **Logistics_DeliveryJob**: The unit of work dispatched to couriers, containing one or more `Logistics_Shipment` records, identified by a `DJB-` prefix.
- **COD OTP**: The cash-on-delivery one-time password flow where the courier requests an OTP for the buyer, and the buyer verbally shares it for verification.
- **Production Plan**: A supplier's production run entity with states DRAFT → SCHEDULED → IN_PRODUCTION → QUALITY_CHECK → READY / REJECTED.
- **Provider**: An internal Maysar ops user with `provider` or `admin` role who manages request assessments and quote creation.
- **Commission**: A ledger entry recording the platform's fee earned on a transaction, queryable per seller via `/api/commission`.
- **Enabler**: A Maysar partner user role with onboarding (approve → terms → activation) and earnings flows via `/api/enabler`.
- **Training Module**: A structured learning unit accessible via `/api/training/api/v1/modules`, completable with assessment submission.
- **ctx**: The shared context object in the script that accumulates entity IDs across lifecycle steps.
- **createdEntities**: The registry of test-created entities that the cleanup phase removes after all lifecycles complete.

## Requirements

### Requirement 1: Request Service Lifecycle — Buyer Side

**User Story:** As a platform operator, I want the lifecycle script to verify the buyer-side request service flow end-to-end, so that I can confirm that custom procurement requests can be submitted, viewed, messaged on, and cancelled.

#### Acceptance Criteria

1. WHEN the script executes the request lifecycle, THE Script SHALL call `POST /api/request/requests` with a valid title, items array, and delivery address as the buyer role and expect a 200 or 201 response.
2. WHEN a request is successfully created, THE Script SHALL call `GET /api/request/requests/:requestId` as the buyer and expect a 200 response.
3. WHEN a request exists, THE Script SHALL call `GET /api/request/requests` as the buyer and expect a 200 response.
4. WHEN a request exists, THE Script SHALL call `POST /api/request/requests/:requestId/messages` with a message body as the buyer and expect a 200 or 201 response.
5. WHEN a request exists, THE Script SHALL call `GET /api/request/requests/:requestId/messages` as the buyer and expect a 200 response.
6. WHEN a request is in a cancellable state (SUBMITTED, ASSESSING, or NEEDS_CLARIFICATION), THE Script SHALL call `POST /api/request/requests/:requestId/cancel` as the buyer and expect a 200 response.
7. IF the request creation step fails, THEN THE Script SHALL log a skip notice and proceed to the next lifecycle without aborting the run.

### Requirement 2: Request Service Lifecycle — Provider/Admin Side

**User Story:** As a platform operator, I want the lifecycle script to verify the provider-side request service flow, so that I can confirm that ops can assess requests, create quotes, publish them, and generate assessment links.

#### Acceptance Criteria

1. WHEN the script executes the provider request lifecycle, THE Script SHALL call `GET /api/request/provider/requests` as the admin role and expect a 200 response.
2. WHEN an unassigned request exists, THE Script SHALL call `POST /api/request/provider/requests/:requestId/assign` as the admin and expect a 200 or 201 response.
3. WHEN an assigned request exists, THE Script SHALL call `POST /api/request/provider/requests/:requestId/assess` with `{ "decision": "FULFILLABLE" }` as the admin and expect a 200 or 201 response.
4. WHEN a request is in FULFILLABLE state, THE Script SHALL call `POST /api/request/provider/requests/:requestId/quotes` as the admin with valid `sellingPriceTzs`, `procurementCostTzs`, `logisticsCostTzs`, `validUntil`, and `items` and expect a 200 or 201 response.
5. WHEN a DRAFT quote exists, THE Script SHALL call `POST /api/request/provider/quotes/:quoteId/publish` as the admin and expect a 200, 201, or 422 response (422 is acceptable when sourcing gate requirements are not met by test data).
6. WHEN a PUBLISHED quote exists, THE Script SHALL call `POST /api/request/provider/quotes/:quoteId/assessment-link` as the admin and expect a 200 or 201 response.
7. IF any provider step fails due to missing prerequisite data, THEN THE Script SHALL skip remaining provider steps gracefully and log the reason.

### Requirement 3: Request Service Lifecycle — Assessment Link and Conversion

**User Story:** As a platform operator, I want the lifecycle script to verify that a buyer can resolve an assessment link and convert a quote to an order, so that the end-to-end request fulfillment path is confirmed.

#### Acceptance Criteria

1. WHEN an assessment link token is available, THE Script SHALL call `GET /api/request/requests/assess/:token` without a Bearer token and expect a 200 response.
2. WHEN a valid unconsumed assessment link token exists, THE Script SHALL call `POST /api/request/requests/assess/:token/convert` without a Bearer token and expect a 200 or 201 response.
3. WHEN the convert call succeeds, THE Script SHALL extract the returned `orderId` and log it to the console.
4. WHEN the convert call succeeds a second time with the same token, THE Script SHALL call `POST /api/request/requests/assess/:token/convert` again and expect a 200 response with `created: false` (idempotency check).
5. IF assessment link generation failed in Requirement 2, THEN THE Script SHALL skip assessment link and conversion steps and log the reason.

### Requirement 4: Logistics Lifecycle Depth — Fulfillment Options

**User Story:** As a platform operator, I want the logistics lifecycle to verify the fulfillment-options endpoint, so that I can confirm that multi-seller cart logistics planning works correctly.

#### Acceptance Criteria

1. WHEN the script executes the logistics depth lifecycle, THE Script SHALL call `POST /api/logistics/v1/fulfillment-options` with a valid items array containing `sellerId`, weight, and destination address and expect a 200, 400, or 422 response.
2. WHEN a 200 response is returned, THE Script SHALL log the count of `options[]`, `exclusions[]`, and `fairnessExcluded[]` arrays from the response.
3. THE Script SHALL NOT treat an empty `options[]` array as a failure — an empty options array with items in `exclusions[]` or `fairnessExcluded[]` is a valid 200 response.

### Requirement 5: Logistics Lifecycle Depth — Delivery Tracking

**User Story:** As a platform operator, I want the logistics lifecycle to verify delivery tracking, so that I can confirm that the delivery status endpoint is reachable and returns expected data.

#### Acceptance Criteria

1. WHEN an orderId from a previous lifecycle step is available, THE Script SHALL call `GET /api/logistics/api/v1/deliveries` or equivalent to list deliveries and expect a 200 or 404 response.
2. WHEN a deliveryId is available, THE Script SHALL call `GET /api/logistics/api/v1/deliveries/:deliveryId` as the buyer and expect a 200 or 404 response.
3. WHEN the delivery tracking call returns 200, THE Script SHALL log the delivery status value.
4. IF no deliveryId is available (order was not successfully placed in earlier steps), THEN THE Script SHALL log a skip notice and proceed.

### Requirement 6: Courier Delivery Milestone Events Depth

**User Story:** As a platform operator, I want the lifecycle script to verify courier milestone status transitions, so that I can confirm that the delivery state machine enforces valid transitions and rejects invalid ones.

#### Acceptance Criteria

1. WHEN the script executes the courier lifecycle, THE Script SHALL call `GET /api/logistics/api/courier/deliveries` as the courier and expect a 200 or 404 response.
2. WHEN a delivery exists in `pending` state and is assigned to the courier, THE Script SHALL call `PATCH /api/logistics/api/v1/deliveries/:deliveryId/status` with `{ "status": "picked_up" }` and expect a 200, 400, or 409 response.
3. WHEN a valid status transition is attempted (e.g., `in_transit`), THE Script SHALL call `PATCH /api/logistics/api/v1/deliveries/:deliveryId/status` and expect a 200, 400, or 409 response.
4. WHEN an invalid status transition is attempted (e.g., jumping from `pending` to `delivered` skipping intermediate states), THE Script SHALL call the status endpoint and expect a 409 response.
5. IF no assignable delivery exists, THEN THE Script SHALL log a skip notice for milestone event steps.

### Requirement 7: Support Lifecycle — Ticket, Disputes, and Dispute Resolution

**User Story:** As a platform operator, I want the support lifecycle to verify ticket management, dispute listing, individual dispute lookup, and dispute resolution, so that I can confirm the full support surface is reachable.

#### Acceptance Criteria

4. IF no disputeId is present in the disputes list, THE Script SHALL log a skip notice for steps 2–3 and continue.

### Requirement 8: Deeper Auth Lifecycle — Token Refresh, Password Reset, and 2FA Backup Codes

**User Story:** As a platform operator, I want the auth lifecycle to verify token refresh, password reset initiation, and 2FA backup code management, so that I can confirm that session management, credential recovery, and all 2FA management flows are reachable.

#### Acceptance Criteria

1. WHEN the script executes the extended auth lifecycle, THE Script SHALL call `POST /api/auth/refresh` with a valid refresh token as the buyer and expect a 200 response.
2. WHEN the script exercises the password reset flow, THE Script SHALL call `POST /api/auth/password/reset/initiate` with the buyer's email address and expect a 200 response.
3. WHEN the script checks 2FA status, THE Script SHALL call `GET /api/auth/2fa/status` or equivalent as the seller and expect a 200 or 404 response.
4. THE Script SHALL re-login the buyer after the password reset initiate call to restore the active session.
5. THE Script SHALL call `POST /api/auth/2fa/backup-codes/regenerate` as the admin and expect a 200 or 400 response (400 is acceptable when 2FA is not enabled for the admin account).

### Requirement 9: Deeper Order Fulfillment — Full State Walk

**User Story:** As a platform operator, I want the order fulfillment lifecycle to attempt all available seller-side order actions, so that I can confirm that seller order management endpoints are reachable and return expected responses.

#### Acceptance Criteria

1. WHEN an order exists in `PENDING_SELLER_VERIFICATION` state, THE Script SHALL call `POST /api/order/orders/:id/verify` as the seller and expect a 200, 201, 400, or 404 response.
2. WHEN an order exists in a verified state, THE Script SHALL call `GET /api/order/orders/:id` as the seller and log the current order status.
3. THE Script SHALL call `GET /api/order/orders` as the admin and expect a 200 response, logging the total count.
4. WHEN no order is in a fulfillable state, THE Script SHALL log the current state of the most recent order instead of failing.
5. THE Script SHALL check admin-level order endpoints: `GET /api/order/orders` as admin SHALL expect a 200 response.

### Requirement 13: Script Structure and Output Format Preservation

**User Story:** As a developer running the script, I want the expanded script to maintain exactly the same output format and structure as the current script, so that existing CI parsing, result file consumers, and developer familiarity are not broken.

#### Acceptance Criteria

1. THE Script SHALL use the same `step()`, `header()`, `api()`, `login()`, and `cleanup()` helper functions as the current script without changing their signatures.
2. THE Script SHALL write the lifecycle results JSON to `docs/verification/lifecycle-results.json` using the same schema as the current script (`runDate`, `baseUrl`, `summary`, `byLifecycle`, `results`).
3. THE Script SHALL maintain the `passed`, `failed`, and `results` counters using the same increment logic.
4. THE Script SHALL exit with code 1 when any step fails and code 0 when all steps pass, matching current behavior.
5. WHEN the script adds new lifecycles, THE Script SHALL assign them sequential IDs starting from LC-11.
6. THE Script SHALL preserve all existing ten lifecycles (LC-01 through LC-10) unchanged in position and content.
7. THE Script SHALL register all test-created entities in `createdEntities` and clean them up in the `cleanup()` function.

### Requirement 14: Graceful Prerequisite Handling

**User Story:** As a platform operator, I want every new lifecycle to degrade gracefully when prerequisite data is unavailable, so that the script never aborts mid-run due to a missing entity from an earlier step.

#### Acceptance Criteria

1. WHEN a new lifecycle requires an entity ID that was not created in a prior step, THE Script SHALL log a skip notice using the `⏭️` icon and push a `{ ok: null }` skip result to the results array.
2. THE Script SHALL continue to the next lifecycle after a skip — it SHALL NOT throw an uncaught exception or call `process.exit()` mid-run.
3. WHEN the script is run against a server with no pre-existing data, THE Script SHALL still produce a valid `lifecycle-results.json` file with skipped steps rather than an error.
4. IF a network error occurs during an API call, THE Script SHALL record the step as failed (ok: false) rather than throwing an uncaught exception, matching the existing error handling in the `api()` helper.
